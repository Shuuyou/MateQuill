# 门店原生视觉：研究、根因与落地（2026-10-24）

本轮先查原始论文、作者项目和官方产品实践，再改创作流程。研究不是对“爆款”“推流”或本项目模型质量的保证。

## 原始依据

- [Qwen-Image-2.1，官方2026-09-20发布](https://qwen.ai/blog?id=qwen-image-2.1)：统一生成/编辑、透明主体、局部标注、多参考与产品一致性是实际能力方向。由此采用“产品、场景和风格参考分别标明职责”，不因图片看起来漂亮就推断身份保真；本轮没有更换现有图像服务或部署Qwen。
- [StableI2I，2026-05-06原论文](https://arxiv.org/abs/2605.04453)：仅看指令遵循和审美会遗漏图像编辑中的语义对应、空间结构和非预期变化。落实为编辑范围、保留对象及实际前后对照；不把本项目现有审查冒称为部署了其评测模型。
- [ContextGen，ICLR 2026作者项目](https://nenhang.github.io/ContextGen/)：布局与实例身份需要明确关联，多张参考不能无区别混在一起。落实为每页实际来源、主要视角、照片证据范围与系列风格参考分工，不跨型号拼接新外观。
- [Google官方图像提示实践，2025-08-26](https://blog.google/products-and-platforms/products/gemini/image-generation-prompting-tips/)：主体、取景、动作、位置、视觉风格和局部编辑应具体。这支持从本次“人要看什么/判断什么”出发写图像任务，而不是堆“高级、专业、电影感”。
- [小红书官方本地经营入口](https://life.xiaohongshu.com/)提供门店/商品/笔记经营链路，但公开页面未给出可验证的流量公式。本轮不从平台经营页面推导“随手拍一定更容易被推荐”，也不盗用品牌或博主图片作为自家素材。

## 代码根因

初读`design_art_direction.py`发现其完整商业重画指令与原生照片方向冲突，但继续追踪发现：当前`execute_design`主流程没有调用`_commercial_treatment`，该分支仅自递归。因此不能声称本轮当前主链“把所有照片都重画了”；本轮不修改这个未调用路径。实际主链是原生规划、原图层合成、可选抽象设计元素，以及真实渲染检查；已有`native_source_proof`保障源素材字节，不能冒称本轮新发明。

真实缺口在`design/planner.py`：虽识别photo/packshot，创作系统词仍主要以商业艺术指导组织叙述，缺少任务型观看方式与实拍保留职责。`_design_elements_treatment`只要有prepared_subject就考虑抽象底板，混合“实拍+产品主体”的页面可能得到无必要的装饰。仅在负面prompt写“不要AI感”无法改变这种选择路径。

## 本轮选择

新增原生视觉合同，以本次明确创作要求、平台承载任务、真实可用照片和可见观察为依据。现场观察、细节标注、选择解释和品牌编辑均是可选创作方式，不把店员永远锁死为低清UGC，也不强迫品牌身份永远做大字KV。实际照片支持的空间范围保留；只有产品参考时，生成画面属于设计，不冒充真实到店、实拍样张或顾客经历。

原生感来自可看见的物件关系、适当观看距离、真实光线逻辑、重点与留白，而不是加假手机边框、点赞数、时间戳、刻意糊图或随机杂乱。标题不必每页重印；不同页应承担观察/解释/补充的实际职责。

接线：规划器payload和系统词 → 实际原生合成 → 抽象底板入口。已有授权实拍、真实photo层和明确照片处理意图同时成立时，不再生成无必要底板；记录既有source proof、显示变换和未生成新图。无实际照片或明确要求重新设计时仍走原设计流程。没有增加每页重抽、额外judge或网络调用。最终文案、几何、来源和实际像素检查继续执行；源字节未变不等于显示裁切之外的像素全等，更不证明拍摄故事真实。

## 验证

113项相关测试通过，覆盖原生方向、元素生成及恢复、门店上下文、原生素材交付与真实临时租户设计链。新测试实际运行`render_document`生成PNG，核对320×320尺寸及源图两个区域的RGB、原始SHA、显示变换、篡改拒绝、恢复不重放和未调用收费图片编辑。该像素源为明确标识的合成测试图，不冒称现场照片或真实观众偏好评测。最终成品的审美与产品身份仍由主协调的少量真实模型验收和人工查看判断。

原图处理证据进入`state.source_preservation[board.id]`与最终`artboards[].source_preservation`；规划合同进入`plan.provenance.native_visual_contract`。如果没有真实照片，合同不会凭标题“本店实拍”制造现场证据。

## 实测暴露的短文案审校协议

主协调真实图制作在规划前遇到独立审稿输出自相矛盾：理由认为支持，纯产品名称却标成`product_claim + not_assertion`；另一次支持重量却未返回引用。保留这些失败，不自动替换分类或补引用。本轮为同一次审校增加逐卡严格schema：真实卡片ID、已绑定事实/门店ID枚举、纯canonical名称的表达分支、实际断言所需非空引用。生产客户端明确启用逐句协议后，所有标题、caption及要点须完整覆盖。原拒绝不会变通过，必要条件仍由原事实与语义检查负责。

协议与设计交付相关83项测试通过。它降低接口含混，不能保证模型必然遵循或证明真实语义已正确；实际模型是否改善由主协调更新冻结源码后再验证。未增加审校调用或在本子任务内重新付费出图。

## 无叠字合同的实际冲突修复

另一真实任务明确要求“无叠字、无标题、无参数和按钮”，但旧服务与规划器只认“无字/不要文字/不加字/纯照片”几个词，实际仍生成了approved标题，再因模型没有排该标题而阻断。已将明确无叠字请求解析集中到同一helper；否定的“不要改成纯照片”、单独“无标题”（仍可能允许caption）、标题引用“无字天书”不触发无叠字处理。

服务仅在实际请求明确无叠字时准备空文案，标记没有进行模型文案审阅；规划器不给叠字catalog，并拒绝新造文字层，最终交付也检查没有visible叠字。普通有字任务继续要求已批准标题，模型或旧数据单独声称no-type不能获得豁免。新的14项测试包含真实临时租户的execute_design、原生渲染、源字节绑定和最终检查；像素审核在此集成测试中使用明确离线夹具，不冒称真实模型审美验收。
